# 工程方案最佳实践原则（MUST · alwaysApply）

## 描述

**所有技术方案只选择最生产化、最工程化、最正确的方案，使用业界最佳实践。禁止使用已被证明存在问题的方案，禁止"临时方案/过渡形态/先这样后续再改"。**

本规则适用于：架构设计、DDD、状态管理、并发模型、持久化、API 设计、测试策略、所有技术选型。

## 适用场景

- 任何方案设计阶段（`/plan-template`、`brainstorming`、技术选型讨论）
- 代码重构决策（如 DDD 改造、分层调整）
- 新功能的技术栈/模式选择
- review 现有代码时发现"过渡形态"需纠正

## 硬约束（MUST）

### 1. 禁止"临时方案/过渡形态"

凡是被描述为以下任何一种的方案，**一律禁止采用**：

- ❌ "先这样，后续再改"
- ❌ "过渡形态" / "临时形态"
- ❌ "简化版，之后升级"
- ❌ "现状如此，先接受"

**理由**：临时方案几乎不会被改掉，会成为永久的债务。"先简单做再优化"是技术债的头号来源。**一次做对**的成本远低于"先做错再返工"。

### 2. 禁止使用已被证明有问题的方案

以下方案在业界已被广泛认定为反模式/有问题，**禁止作为新方案采用**（现有代码中存在的，应在重构时纠正）：

| 反模式 | 正确做法 |
|--------|---------|
| **贫血模型 + 胖 Service**（Entity 无行为，业务逻辑全在 Service） | 充血模型：聚合根封装不变量+行为，Service 仅用例编排 |
| **静态工具类伪装的"聚合根"**（全 static 方法，无状态，外部直接操作 Entity） | 真聚合根：持有聚合内实体引用，行为修改内部状态 |
| **聚合间直接调用对方 Service**（TemplateService 注入 PageService） | 领域事件解耦（聚合根发布事件，对方订阅） |
| **domain 层带框架注解**（@Service/@Component 在 domain 包） | domain 层零框架依赖（纯 POJO） |
| **状态机散落在 if-else** | 显式状态机（状态表 + transition 函数 + 非法转移抛异常） |
| **手写级联删除脚本** | 聚合根事务边界封装级联不变量 |
| **SharedMutableGlobal / 单例可变状态** | 不可变值对象 + 显式传递 |
| **God Service**（一个 Service 干所有事） | 按领域拆分 + 应用服务编排 |
| **事务脚本式 Service**（纯过程式无对象） | 面向对象领域模型 |

### 3. 方案评估必须列出"为什么不选其他方案"

定稿方案时，凡涉及关键技术决策，须写明：
- 选择了什么方案
- **为什么选它**（业界最佳实践依据）
- **为什么不选其他方案**（被排除方案的问题）

### 4. "现状"不等于"正确"

review 现有代码时：
- ✅ 客观陈述现状（"当前 LeadStatusMachine 带 @Service，违反 domain 纯净"）
- ❌ 把现状当作设计基础（"现状是静态工具类，所以新聚合根也用静态工具类"）

**现状是待纠正的债务，不是方案的起点。** 新方案应直接采用最佳实践，即使改动量更大。

## DDD 专项约束（本规则下 MUST）

DDD 改造时，聚合根必须满足以下全部条件，缺一不可：

1. **真聚合根**：持有聚合内实体的引用（而非静态方法操作外部 Entity）
2. **充血模型**：业务行为（不变量校验、状态机、级联）封装在聚合根方法内
3. **domain 零框架依赖**：聚合根无 Spring/MyBatis/Jakarta 注解（纯 POJO）
4. **final 类**：防继承破坏不变量
5. **工厂方法**：`reconstitute()`（从持久化重建）+ `newXxx()`（创建），构造器非 public
6. **聚合间通过领域事件通信**：禁止聚合根 A 直接持有/调用聚合根 B 的 Service
7. **仓储分离**：聚合根不依赖 Mapper（由 Service/Repository 负责持久化）

## 违反处理

- 方案评审阶段发现违反：**方案作废重做**
- 代码已写发现违反：**重构纠正**，不允许"先合入后续再说"
- Agent（含子 agent）方案输出违反：主会话须驳回并要求重新设计

## 与其他规则的关系

- 本规则优先级高于"工作量/进度"考量：宁可范围缩小做对，不可范围做大做错
- 与 `luban-no-speculation-no-blind-dev.md` 互补：前者管"信息完整"，本规则管"方案正确"
- 与 `self-improve.md` 联动：发现新的反模式时补充到本规则
